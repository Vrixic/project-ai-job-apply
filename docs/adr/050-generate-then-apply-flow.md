# ADR-050: Generate-then-apply flow, server-side material reads and PDF-only delivery

Status: Proposed (owner-directed 2026-10-20); locally verified source, default-off pieces, live acceptance pending
Date: 2026-10-20

## Context

The candidate flow had four rough edges. Reading a generated resume needed a second, popup Auth0
sign-in held in browser memory for ten minutes ([ADR-044](044-browser-native-material-identity.md)).
A generated resume had no honest status: a failed or slow preparation showed the same "may still be
preparing" text, and a manual "Check generated resume" button was the only refresh. Applying took an
approval ceremony ("Approve this packet", "I reviewed this generated resume", cancel, replace
checkbox). Generated resumes were offered as PDF and DOCX, and the extension had no way to attach
the candidate's own resume when none was generated. The owner asked for the jobright.ai shape:
read the job, then either Generate (a loading step that resolves by itself) or Apply directly, and
Apply takes the candidate to the employer page with the extension already knowing which resume to
use.

## Decisions

1. **The browser holds no material credential.** Generated material is read through one same-origin
   BFF route per kind (`/api/platform/applications/{id}/{resume|cover-letter}/content`). The server
   uses the signed-in candidate's own server-held access token, never exposing it. It reads the
   scalar location proof from the Gateway, validates that the origin is a UUID allocation under the
   configured native base host on port 8443, performs the native read (no cookies, redirects or
   referrer; 15 seconds; 512 KiB), verifies the closed response schema, the exact original material
   identity, the content hash and the packet hash, then re-reads the location proof. The native
   process still authorizes every read itself (exact issuer, audience, scope, expiry and owner) and
   fails closed; the original 30-minute expiry, owner binding and purge behavior are unchanged.
   This supersedes ADR-044's separate SPA registration, popup sign-in, ten-minute credential lease,
   COOP `same-origin-allow-popups` exception and `NEXT_PUBLIC_NATIVE_AUTH0_*` variables.
   - Trade-off: generated bytes now pass through Vercel function memory on the way to the browser,
     where ADR-040 kept them out of Gateway/Lambda copies. They are bounded (512 KiB), streamed
     once, `no-store`, never logged or persisted, and exist only for one request. This extends the
     existing web hosting subprocessor's role and is a privacy-review item before activation.
   - Residual: the native host receives the candidate's Gateway-audience access token (the same one
     the BFF uses for the Gateway), because the native process accepts that audience today. A
     compromised or briefly mis-resolved allocation host could therefore see a token valid for the
     whole API until it expires. The allocation allowlist (exact HTTPS, port 8443, UUID label under
     the reviewed base host, no redirects) limits this. A dedicated native audience with a
     material-read-only scope would remove it and is the recommended follow-up, needing tenant and
     native image changes.
   - Rejected: a BFF-minted browser token (needs a new trusted issuer in the native image, tenant
     configuration and a broader-than-necessary credential in the browser); handing the browser the
     confidential web access token (a broader credential); keeping the popup sign-in.
2. **Apply is the candidate's approval act; the server invariant is unchanged.** The immutable,
   hash-bound packet and approval records, the 24-hour and 30-minute expiries, stale-binding
   refusal and duplicate-attempt guards remain server-enforced. What is removed is the user
   ceremony. Pressing Apply approves the packet built from the candidate's saved answers; checks and
   the resume preview belong to the packet that was on screen, so a packet rebuilt during the click
   inherits none of them and Apply stops to show it. Automatic answers that need no review are not
   itemised before a first Apply. Limits:
   - Answers that need the candidate (empty direct-action fields) and sensitive, restricted or
     uncertain answers still require explicit entry or an explicit per-answer check before Apply is
     enabled. Their acknowledgements are sent exactly as checked.
   - The `documents.resume` field (always "explicit each time") is acknowledged by Apply itself,
     only when the resume identity is shown beside the button and, for a generated resume, its exact
     preview was displayed to the candidate in this session. The uploaded resume is named at Apply.
   - The cancel action and the replace-while-running checkbox leave the UI; the routes remain for
     reconciliation and API clients. The panel after Apply is minimal: the employer link, one line
     naming the resume the extension will use, and a Record submission button that opens a dialog.
     Search holds only jobs that were not applied to: once a submission is logged the job leaves the
     search results at once (and stays out of later searches), and it is listed under Applied.
     The dialog opens by itself when Apply sends the candidate to the employer's page, so it is
     waiting when they return; Cancel dismisses it and the button reopens it.
     The dialog records the outcome in one step (I submitted it / It was not submitted); the earlier
     second "Before you apply" panel and its duplicate-risk checkbox are gone. The duplicate-risk
     acknowledgement the server requires for "not submitted" is now a line of text in the dialog and
     the deliberate click on that button.
     The pasted-link "Continue with the extension" panel, the copy-by-hand answer list, "Stop
     waiting" and "Choose a different resume" are removed from it; reopening still invalidates the
     approval as before.
   - The optional cover letter is its own step laid out like the resume step: one short line
     ("Generates a cover letter based on your resume and the job description.") and one Generate
     cover letter button. The owner chose to state nothing about the provider, retention or what is
     sent on this page. The request still carries the disclosure version the Gateway requires with
     `acknowledged: true`, but the candidate no longer sees that notice here, so the notice and its
     consent must be presented elsewhere (sign-up terms or privacy policy) before activation. This
     is an open privacy-review item. Because the Gateway builds the cover letter with a generated
     resume in one packet, generating a cover letter also generates the resume.
3. **Generation state is honest and server-derived.** Applications exposes an additive
   `resumeGeneration` (`not_requested | preparing | ready | failed | expired`, with an error code and
   request time) derived only from owner metadata (the current packet's generated material and the
   newest generation request). It carries no task or provider detail. Failure is reported from a
   failed delivery, a missing uploaded resume, a terminal execution observation, a candidate
   withdrawal, or a bounded timeout (10 minutes). The UI polls the application itself.
4. **Generated resumes are PDF only** across the preview, download, native read and extension
   transfer contracts, the native process's completion verification and the Documents tailoring
   runtime. Cover letters are out of scope and keep their own formats. The candidate's uploaded
   resume keeps its original format.
   The web preview is that same PDF drawn page by page in the browser (PDF.js on the page's own
   thread, no blob URL, plugin or CSP change), read once and held in memory only while shown, so the
   candidate reviews exactly the file that Download and the extension use. The download and
   attachment name is always built by the web app as `User_Job_Name_ID.pdf` (candidate name from
   the session, job title, application id), never taken from the generating process. The earlier
   bullet-by-bullet text preview is no longer shown.
5. **The uploaded resume fallback is an owner-scoped original read.** `PrepareApplicationPacketRequest`
   gains `resume: generate | uploaded`. `uploaded` creates no generation request, binds the original
   file's SHA-256 as the packet's resume hash with a reviewable `documents.resume` field, and the
   new `GET /applications/{id}/resume/uploaded` serves the exact original bytes only for a packet
   bound to them (size cap 2 MiB, never cached). The Documents processor reads the exact stored
   object version through the reviewed object-access role with an exact-object session policy (the
   parser's own mechanism; the processor already assumes that role, so no IAM change is expected, to be confirmed by policy simulation at release), verifies size and digest, and returns the bytes only to
   the owner's request. It is default off (`UPLOADED_RESUME_ATTACHMENT_ENABLED`) and needs a
   Documents release and owner security review before activation.
6. **Extension hand-off: arm, then confirm.** Pressing Apply opens the employer page from the click
   and sends the extension an identifiers-only `application-apply-intent.v1` over the existing
   first-party channel. The extension reads the packet with its own session and derives the resume
   from the packet (generated file or uploaded original), shows the intent to the popup, and the
   candidate confirms on the employer tab (activeTab grants only after that click; no manifest or
   permission change). The website pushes the generated PDF when the extension is ready; the
   extension pulls the uploaded original itself. An expired generated resume is never sent; Apply
   falls back to the uploaded resume or offers a fresh Generate.

## Not changed, and a discrepancy for the owner

Resolved 2026-10-22 by [ADR-053](053-candidate-approved-submission-greenhouse-and-ashby.md): the owner
chose the click, so the stated rule changed and not the code.

The Greenhouse execution path (ADR-049) clicks the employer's submit control once when no challenge
is present, then waits for provider confirmation. That contradicts the stated rule that the
extension never clicks the final submit. It is dark in every build (the production application
profile registry is empty) and this ADR does not change it. Making the rule true means filling and
attaching, then handing every page to the candidate the way a challenge page already is; that is a
separate decision against ADR-049 and ADR-046.

## Consequences

- Native image: this ADR also removes DOCX rendering from the resume completion check. The live
  image predates the leading-bullet fix (#701), so one governed image release is needed anyway; this
  change is compatible with the live image (the web no longer requests DOCX) but is not exercised
  by it until that release.
- Deployment order: Documents processor (original read) and Gateway (new route, `resume` option,
  generation status) before the web release; the BFF needs `NATIVE_MATERIAL_BASE_HOST`. The Auth0
  SPA registration from ADR-044 is no longer used and can be retired by the owner.
- The generation state reads the newest generation request of the application, not one tied to a
  packet id, so a packet without any resume binding can show an older request as preparing for at
  most the 10-minute timeout. Uploaded and generated packets always carry a binding.
- Failure detection latency for a lost generation depends on the existing execution observer
  cadence; the bounded timeout caps what the candidate waits.
- All checks use synthetic identity, BFF and native responses. Live token acceptance by the native
  process, installed-extension behavior, provider retention and accountable reviews remain open.

## Amendment 2026-11-05: Apply waits for the profile basics

Owner direction: the answers an application form always asks come from the candidate's ApplyDash
profile, are collected from every new candidate, and no one applies until they are all there. The web
now checks the saved profile (`lib/application-basics.ts`, `useApplicationBasics`) and holds the Apply
button, with the missing items named and linked to the Profile, until it holds a first and last name,
an email, a phone number, one education entry with school, degree and field of study, and, while the
saved-answer vault is offered, saved answers for United States work authorization and visa
sponsorship. A profile that cannot be read pauses Apply (fail closed). Nothing is inferred or filled
in for the candidate. Using the saved authorization answers to answer the employer's own questions is
a separate decision (ADR-010 treats them as restricted) and is not part of this change.
