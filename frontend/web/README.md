# Web Application

The primary candidate experience: onboarding, profile management, job discovery, application review, technical history through confirmed submission, outreach, billing, settings, and crawlable public job pages.

## Planned subfolders

- `app/` — Next.js routes, layouts, server components, and route handlers.
- `features/` — Product modules such as jobs, applications, profile, and billing.
- `components/` — Web-only composed components.
- `lib/` — Generated API clients, session helpers, and browser-safe utilities.
- `public/` — Static assets.
- `tests/` — Unit, accessibility, integration, and browser tests.

The web app orchestrates presentation only. Long-running preparation and submission work is started through backend APIs and displayed as durable workflow state.

## Phase 0 implementation

The initial responsive route restores and saves owner-scoped target roles, locations, and work
mode, then polls the durable readiness operation. A returning authenticated candidate sees the
last persisted preference set rather than presentation defaults. It displays the unresolved
identity-provider gate and never enables a production test-auth bypass.

Auth0 sessions are held by the Next.js server boundary. The browser calls narrow `/api/platform`
BFF routes, which attach an access token server-side and forward only approved headers to the
gateway. Configure the isolated development tenant through the
[development runbook](../../docs/security/auth0-development-runbook.md); never expose tokens
through `NEXT_PUBLIC_*` variables or browser storage.

While running through `next dev`, an authenticated synthetic user also sees a development-only
session-renewal conformance control. It forces the server-held token set to refresh and returns
only a sanitized pass or reauthentication-required result. The route returns `404` outside the
local development runtime and rejects cross-origin requests.

The same panel can prove the deployed `jobs:read` permission without exposing the access token. It
calls a structurally valid identifier that cannot be generated by the UUIDv7 catalog and passes
only when the authenticated active-job route returns `404`; `403` is reported as a missing scope,
and an unexpected record fails closed.

The same development panel includes a deployed cross-user isolation probe. The first synthetic
account arms a completed operation, logs out, and a distinct synthetic account runs the check.
The server verifies first-account ownership before sealing the operation reference and a keyed
identity fingerprint into a 15-minute, HTTP-only, same-site cookie. The check passes only when the
deployed API returns `404` to the second account. Neither token, identity, operation identifier,
nor response body is returned to browser code or retained as evidence.

Use `scripts/start-deployed-web-conformance.ps1` to route this local, server-held BFF to either
development or synthetic staging. The launcher verifies that the selected live gateway has the
same issuer and audience as the ignored local Auth0 configuration, confirms the immutable Lambda
alias and durable triggers, rejects any continuous ECS application path, and requires
`200/200/401` before it starts. Staging's temporary use of the development Auth0 tenant is
synthetic-only under ADR-014 and does not prove identity-provider isolation or launch readiness.
The isolation probe always requires a terminal `succeeded` operation; retired transition modes
cannot be selected.

Authentication callback failures redirect to an allowlisted local error state. Provider-controlled
error descriptions are never rendered, while blocked or unavailable accounts receive a generic
recovery message.

Presentation branding comes from `@ai-job-apply/config/brand` and can be overridden at build time
with `NEXT_PUBLIC_PRODUCT_BRAND_NAME` and `NEXT_PUBLIC_PRODUCT_BRAND_DOMAIN`. The domain value is
descriptive only until ownership and public-brand approval are recorded; API and web origins use
separate configuration.

## Phase 1 implementation

The truth-profile panel uses server-held Auth0 sessions to list, create, correct, and reject
candidate-owned facts. Direct entries are clearly described as user-confirmed; correction creates
a new version and the browser supplies no identity or provenance claim. Direct entries are fixed
to the Confidential class. The general profile form does not collect Restricted sponsorship,
work-authorization, demographic, disability, veteran, or legal answers; that capture remains
deferred to the dedicated D3 restricted-data boundary and mandatory review flow.

The local-only expanded onboarding editor starts with no fabricated preference values, uses
separate array-backed controls for up to ten target roles and ten optional locations, preserves
entry boundaries, commas, and line breaks while trimming entry edges and deduplicating exact
entries, and supports ordered multi-choice work modes and employment types plus an optional
all-or-none minimum-compensation amount/currency pair. It does
not display, collect, or submit sponsorship. Because the current preference `PUT` is a full
replacement, any loaded legacy preference containing either sponsorship boolean is detected
without displaying the answer and saving fails closed until that field is migrated to the future
restricted-data boundary. This packet is locally verified source only; real-browser, managed-OIDC,
deployment, and real-candidate acceptance remain open.

The deployed development
intake flow issues a direct, five-minute, write-only quarantine upload grant and lists only
candidate-owned document metadata. Scan-result consumption, isolated parsing, and proposed-fact
review are implemented, and the isolated processor/parser infrastructure is deployed CompleteDark
in development with its event-source mapping, GuardDuty rule, and reconciler disabled. The
generated-synthetic direct-dark acceptance source packet merged through PR #280 at `8965d8f` and
is locally verified. Its immutable migration image and task definition remain unpublished;
production container smoke/scan and AWS execution/acceptance remain unrun. Its direct Lambda calls
fabricate an already-validated
authorizer context and do not prove API Gateway routing, JWT/JWKS validation, or authorizer
enforcement. The separately human-reviewed activation sequence remains open, so the end-to-end
proposal flow is still unavailable to users and real resumes remain prohibited.

The first catalog-discovery slice adds a responsive, labelled search form and compact active-job
summaries. The browser sends supported keywords and title, company, location, or freshness filters
only in a bounded JSON body to a narrow server-side BFF. Auth0 tokens remain server-held, raw query
strings are rejected, and pagination uses the API's opaque cursor. Results are explicitly
non-personalized and do not use profile facts.

Active search results expose a candidate report control backed by the existing authenticated
`jobs:write` report contract. The web boundary permits only six fixed catalog-issue reasons, keeps
candidate identity server-side, authenticates before consuming a timeout- and size-bounded
streaming body, validates and redacts responses, and reuses one idempotency key when an ambiguous
attempt is retried without changing the job or reason. It does not collect free text, reveal
moderation state, or automatically suppress a job or source. This is source-only web behavior with
no admin surface, permission grant, deployment, real-report use, or moderation-policy approval.

The saved-job source slice adds a server-held-session BFF, per-result Save control, and a private
owner-scoped list with removal. Historical bounded snapshots remain visible when a posting is no
longer active, and each explicit requested target remains independent. The UI requests the
distinct `jobs:write` permission but does not grant it: the managed Auth0/Terraform permission,
deployment, and live browser acceptance remain later gates. No matching score, explanation, or
application/post-submission state is shown or inferred.

Available saved jobs and active search results now offer an on-demand deterministic match-evidence
panel through a strict server-held-session BFF. Search remains non-personalized: it does not request
private match evidence until the candidate explicitly asks on one result, and an assessment does
not filter, reorder, score, or gate saving. The panel renders fixed constraint labels only, aborts
and generation-fences requests across job changes, announces loading and result state, and discards
a response whose requested identity does not match the panel. It explicitly distinguishes exact
known conflicts from unknown evidence and does not render a score, rank, fit band, eligibility
decision, generated prose, or application outcome. Product and QA accepted the exact immutable v1
generated-synthetic corpus, all-or-nothing rubric, gate semantics, and fixed copy; database
migration, artifact publication, deployment, managed-OIDC browser acceptance, broader matching
quality, and production behavior remain open.

The entitlement status slice uses the same server-held session to call one exact, bodyless
`/api/platform/entitlements` BFF route. It renders only the current derived Free/Pro active or grace
status, clears and aborts state across authentication transitions, and states that both plans
currently contain the same four core capabilities. It has no upgrade, price, quota, checkout,
payment-provider, or paid-feature behavior. Source composition and local tests are not an Auth0,
Terraform, image-publication, AWS deployment, real-browser, or live-entitlement claim.

The source-only `/jobs/{lowercase-uuidv7}` page reads the dedicated anonymous public projection
without cookies or authorization, redirects reversible aliases temporarily to the current
canonical identifier, and renders the employer description as plain text. Canonical metadata uses
only the configured trusted application origin. Crawlers are denied globally by default; an exact
gate may allow only `/jobs/` after separate publication review. No `JobPosting` JSON-LD, sitemap,
Indexing API, application action, employer-original posting date, structured location assertion,
or search-engine eligibility is claimed. No route, Lambda artifact, database identity, bootstrap
boundary, Terraform change, or crawler policy is deployed by these source bytes.

`pnpm test:d1-public-job-page-assurance` builds the production Next application and exercises that
public page in a locally installed Chrome browser against a loopback-only, generated-synthetic
public projection. It covers canonical metadata with indexing disabled, temporary alias
redirection, generic handling of a generated-synthetic expired target and an invalid identifier,
credentialless upstream reads, plain-text description rendering, default crawler denial,
automated WCAG A/AA rules, and a bounded local request burst. The harness and its synthetic values
remain outside the production web package; its typed expired-target stub does not prove backend
lifecycle filtering.

This local assurance is not a deployed route, gateway, Lambda, database, security-header, WAF,
throttling, abuse-control, capacity, provider, or production-data check. It does not approve a
public origin or brand, crawler activation, search-engine eligibility, legal publication,
`JobPosting` JSON-LD, human accessibility, assistive-technology support, or a real job page.

## D1 local browser assurance

`pnpm test:d1-browser-assurance` runs generated-synthetic keyboard, focus, live-region, error
redaction, session-fencing, request-transport, and automated WCAG A/AA checks against real candidate
components. The bounded direct Playwright Core and axe-core harness lives under
`scripts/tests/d1-browser-assurance`, outside this production web package and its deployment closure.

The suite requires a local Chrome binary and never downloads one. It is not human accessibility
acceptance and does not exercise managed OIDC, a deployed BFF/gateway, deployed security headers,
assistive-technology combinations, visual regression, mobile browsers, or real candidate data.

## D1 deployed read workload

`/d1-conformance` is absent unless the local Next development server starts through
`start-deployed-web-conformance.ps1 -EnableD1WorkloadConformance`. After the launcher validates the
exact AWS/Auth0/API Gateway boundary, an approved synthetic managed-OIDC session can run a fixed
150-public/100-authenticated request profile across health, denial, preferences, entitlements,
canonical search, and saved-job reads. Four exact generated response schemas must pass before load.
Concurrency is fixed to the environment's deployed gateway ceiling, every request is bounded, a
second run is rejected, and only aggregate counts/timestamps/latencies are rendered.

The token remains server-held. No identity, candidate value, preference, job, saved job,
request/response body, provider record, or cloud identifier enters the result. This profile performs
no product mutation. Empty search/saved-job results remain valid, so this is not by itself the final
representative-data, provider-failure, write/recovery, SLO, or Phase 1 acceptance gate. See the
[development D1 read-workload runbook](../../infrastructure/runbooks/observability/development-d1-read-workload.md).
